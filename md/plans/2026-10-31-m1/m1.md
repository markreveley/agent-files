# M1 plan — the first build

> Status: done · 2026-11-04 · built (the build spec wins where they differ); companion to [ARCHITECTURE.md](../../governance/ARCHITECTURE.md) §14
> Build spec: [m1-build-spec.md](../../docs/m1-build-spec.md)
> Goal: the smallest agent-files that is worth using every day: threads you can edit as context, a runner for them, a Neovim plugin, and observed status for Claude Code sessions.

**Summary.** M1 is the first build. It ships the thread format, a replay runner (`agent-files-run`), a minimal Neovim plugin (`agents.nvim`) and observe-only hooks for ordinary Claude Code sessions (`agent-files-hook`). Interactive `claude` and `codex` sessions run in Neovim's terminal buffers, and Rex keeps Neovim alive when the terminal app quits. This doc holds the scope of the build and the reasons for it; [m1-build-spec.md](../../docs/m1-build-spec.md) holds the details. What comes after M1 is in [ARCHITECTURE §14](../../governance/ARCHITECTURE.md#14-milestones). The file format is the contract, so scripts can be replaced later without touching a single thread.

## 1. Why these parts

The thesis is that context you can edit as a file beats an append-only chat. M1 builds what that needs, and nothing more:

- **Context editing.** You edit above `END` when it helps: delete a tangent, fix a premise, compress an output. The next turn sends the edited file.
- **Clean forks.** A long thread that drifts becomes a fork that starts from a small `## carry` section, not from the whole history.
- **Cross-thread search.** Threads are plain text, so `rg` across `threads/` finds and reuses earlier work.

Attention for Claude Code sessions is not designed separately: their observed threads (§3.3) show up in the same marks and needs-you list as agent-files' own threads.

## 2. Scope

**In M1**

- The thread format (ARCHITECTURE §4): the root at `~/agent-files/` (its own git repo), thread directories, `thread.md` with the turn grammar (§4.3), the `status` and `seen` sidecars, `## carry`, `steps/`.
- `agent-files-run` — the runtime for `direct` replay threads (§3.1).
- `agents.nvim` — a minimal plugin (§3.2).
- `agent-files-hook` — `observed` status for ordinary Claude Code sessions (§3.3).
- The record in git, search and a spend report (§3.4).

**Not in M1** (later milestones)

- The supervisor, sub-threads and the inbox (M3).
- Tier-2 headless harnesses (Agent SDK, Codex, ACP).
- Tools in the runner — M1 threads are conversation only, so there are no tool folds and no permission questions.
- Grounding, the knowledge base, council, compaction.
- Multi-machine use of agent-files' own runtimes.
- The HTML view (`agent-files-render`, [view-layer.md](../../docs/view-layer.md) step 2): optional, may be prototyped alongside M1.

**Dropped (2026-11-01), not deferred** ([host-analysis](../../docs/host-analysis.md)): the tier-1 interactive bridge (M2); the doorbell (`agent-files-ring`, editor registry, `agent-files-notify`); the Elixir supervisor.

**Added after the first build:** `agents.term`, which reads and types into harness terminals inside Neovim (ARCHITECTURE §11.2), and the session sidebar, which starts, lists and switches the `claude` and `codex` sessions in Neovim ([plan](../2026-11-04-nvim-sidebar/nvim-sidebar.md)).

## 3. Deliverables

### 3.1 `agent-files-run` — the replay runtime

A single executable script (Python, a few hundred lines). Per principle 3 it is just a program on `PATH`; the later supervisor can replace it without changing any file. It is the **single writer** of every thread whose `runtime:` is `direct` (ARCHITECTURE §4.4).

- **Modes:** `agent-files-run watch` (long-running, watches `~/agent-files/threads/`) and `agent-files-run once <thread id>`.
- **Send detection:** after a save, the last turn is yours, ends with `END`, and `status` is not `working` (ARCHITECTURE §4.3). A draft without `END` sends nothing.
- **Assembly (replay):** the agent's system prompt (`agents/<agent>.md`, or a default) → the `## carry` section, if any → every turn in order. The file *is* the context, so whatever you edited above `END` is what the model sees.
- **On a send:** write `working` to `status`; append `## agent · tN`; stream the reply, escaping any line that would parse as a marker; append `END`; append the scaffold `## you · tN+1`; write `done` to `status`; write `steps/tN.request.json` and `.response.json`; `git commit` in the root repo.
- **Interrupt:** if `STOP` appears in the thread directory, stop streaming, append `END (interrupted)`, write `interrupted`, delete `STOP`.
- **Conflicts and crashes:** a foreign write to `thread.md` mid-turn closes the turn with `END (conflict)`; on start-up, any `direct` thread left `working` is closed with `END (interrupted)` (ARCHITECTURE §4.5 rules 1, 3).
- **Model switching:** change `model:` in the frontmatter; the next turn uses it.
- **Backends** (chosen by `model:`):

| Backend | Cost (as of 2026-10) | Exact request in `steps/`? | Notes |
|---|---|---|---|
| Anthropic Messages API (API key) | API rates; cache writes 1.25×, reads 0.1× | Yes | Cleanest replay |
| OpenAI-compatible endpoint (Ollama, LM Studio, llama.cpp) | Free locally | Yes | Good for cheap iteration |
| `claude -p` | Draws from the Pro/Max plan's limits (the separate Agent SDK credit announced 2026-05-13 was paused 2026-06-15) | No — Claude Code adds its own prompt and tools | Verify flags at build time |

### 3.2 `agents.nvim` — minimal plugin

A few hundred lines of Lua.

- Detect `threads/**/thread.md`; `autoread` plus one `vim.uv.new_fs_event` watch per thread directory.
- Buffer read-only while `status` is `working`; on reload, re-apply an unsaved draft below the new last `END`.
- Tabline / statusline mark per thread from `status` and `seen`; a `working` status older than 10 minutes is marked stale (an interrupted observed session, §3.3); a rough token count of the thread (characters ÷ 4) so carried context has a visible cost.
- Commands:
    - `:AgentsSend` — append `END` to your turn and save.
    - `:AgentsStop` — `touch <thread dir>/STOP`.
    - `:AgentsNew <name>` — create `threads/<name>/thread.md` with frontmatter (`runtime: direct`, `context: replay`, `kind: main`) and `## you · t1`.
    - `:AgentsFork` — from a visual selection: create `<thread>/<child>/thread.md` with `kind: fork`, `branched_at: tN`, the parent's settings except `session`, a `## carry` section holding the selection, and `## you · t1`.
    - `:AgentsNext` / `:AgentsBlocked` — needs-you list in quickfix.
    - `:AgentsGrep <pattern>` — `rg` across `threads/` into quickfix.
- Viewing a thread touches its `seen` file (your acknowledgment; ARCHITECTURE §4.5 rule 8).
- Thread-aware display ([view-layer.md](../../docs/view-layer.md) step 1): highlights for turn headers, `END` and `▸` lines; `▸` folds closed by default; the thread's status as virtual text on the last `END`. View-layer step 0 (a markdown renderer, table formatter and buffer settings in your Neovim config) is done before the smoke test.

### 3.3 `agent-files-hook` — observed status

Configured in `~/.claude/settings.json` for ordinary interactive `claude` sessions. It sends nothing to Claude; it only mirrors status, and it is the single writer of its observed threads.

- On a session's first event it creates `threads/_observed/<project>-<session short id>/` with a frontmatter-only `thread.md` (`runtime: observed`, the transcript path).
- Writes `status`: `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure` → `working`; `PermissionRequest`, or `Notification` with `permission_prompt` → `blocked`; `idle_prompt` ignored (it fires ~60 s after a finished turn); `Stop` → `done`; `StopFailure` → `failed`; `SessionEnd` → deletes the directory (verified against the hooks reference, build spec §6).
- Known gap: `Stop` does not fire when you interrupt with Esc (documented), so an interrupted session stays `working` until its next event; the plugin marks it stale after 10 minutes.
- Works the same wherever `claude` runs (a Neovim terminal buffer, a Rex pane, a bare terminal): hooks are configured in Claude Code, not in the host. Rex's own integration adds a separate `SessionStart` entry; both run (ARCHITECTURE §5.1).

### 3.4 The record, search and spend

- **Git history.** The runner commits at every `END` in the root repo, so every edit above `END` is in the history as a commit that changes or deletes lines instead of only appending.
- **`agent-files-grep`** runs `rg` across `threads/`; `:AgentsGrep` calls it.
- **`agent-files-stats`** reports threads, turns per thread and spend.

## 4. How it is meant to be used

- **Use it for** discussion, research and design threads, where context editing matters. Heavy coding stays in the Claude Code or Codex TUI, in a Neovim terminal buffer, observed through hooks.
- **Habits worth building:** start each new question as a thread; when a thread drifts, fork with a `## carry` section before continuing; search old threads before asking again.

## 5. Design risks

| Risk | Mitigation |
|---|---|
| Replay re-sends the whole thread every turn | Local models or `claude -p` for cheap iteration; a daily spend cap in config |
| Frequent `:w` while composing sends half a turn | Sending needs an `END` line; saving alone sends nothing |
| Threads are unpleasant to read in Neovim | View-layer steps 0–1 are part of the build |

## 6. Triggers for a long-lived supervisor

Replace the scripts with a long-lived supervisor process only when one of these is *real*, not anticipated. First check whether an existing tool already covers it, for example TUIOS's headless protocol panes (`start-agent --protocol acp|codex`):

- Routinely more than ~5 headless agents running at once, and the scripts' process handling hurts.
- Crash-recovery or restart bugs are costing real time.
- Tier-2 harness sessions must stay alive across many turns (long-lived SDK clients).

Multi-machine is no longer a trigger: harness sessions on other machines run under Rex's remote hosts, and agent-files' own runtimes run on one machine. The Elixir target is dropped (ARCHITECTURE §10.2). Until a trigger fires the file format is the contract: replacing scripts never touches a thread.

## 7. Effort

Under a week: runner about a day, plugin one to two days, hooks and stats half a day, smoke test half a day.
