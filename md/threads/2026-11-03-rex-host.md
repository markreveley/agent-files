Rex is tmux-style: a background server owns the terminals, and the app is just a viewer that connects to it. I got this from the guide built into Rex's command-line tool. Here's what that gives you over plain Ghostty.

**1. Persistence (the thing you're missing)**
- In Ghostty, the terminal processes belong to the app. Quit it or have it crash, and your nvim and the agents inside it die.
- In Rex, the server keeps your sessions running when the app closes. Reopen it and everything is where you left it, including nvim's `:terminal` agents.
- You don't have to change your workflow to get this. Run your current nvim setup inside a Rex session and you get tmux-style persistence.
- It probably doesn't survive a reboot of the machine running the server, since a reboot kills the server process. I haven't tested that.

**2. Remote hosts**
- A remote host is a Rex server running on another machine. The sidebar groups sessions by host: "laptop" is this Mac, and "rolling-pine" is another server.
- Sessions on a remote host run on that machine. You can close your laptop, reconnect from somewhere else, and the agents have kept working the whole time. It's like ssh + tmux, but shown as native tabs in the app.

**3. Sessions**
- A session is a named workspace, like a tmux session. One per repo would replace your Ghostty tabs.
- Inside a session, a "window" is a tab and a "block" is a pane.

**4. Inter-agent communication: yes, with a catch**
- Rex has a command-line tool that any process can use. An agent can read another pane's whole scrollback (`rex capture`), type into it (`rex send` / `send-key`), open tabs and splits, and wait for a command to finish. That's tmux's `capture-pane` / `send-keys`, plus structured JSON output.
- So one agent could watch another agent, or a test run, and act on what it sees. Ghostty doesn't offer that level of control.
- **The catch:** your agents live inside nvim's terminal splits, so Rex sees only one pane running nvim. Reading that pane gives you only nvim's current screen, with no per-agent scrollback, and anything typed into it goes to nvim.
- To use this between agents, they'd have to be real Rex panes rather than nvim splits. That breaks your `ctrl+w h/l` movement between files and agents, unless you remap Rex's pane keys to match. Plugins like vim-tmux-navigator solve this for tmux. I don't know whether Rex has an equivalent.

**What I'd do:** run your nvim setup unchanged inside one Rex session per repo, which gets you persistence for free. Move only the agents that need to talk to each other into their own Rex panes, if you ever need that. Your agent-files README already names TUIOS as the host for these sessions (via `host-analysis.md`), so Rex is a competing choice for the same role.

The `rex` command isn't on your PATH, so agents can't call it yet. It's inside the app at `/Applications/Rex Beta.app/Contents/Helpers/Rex Server.rex/Contents/MacOS/rex`. Symlinking it into your PATH would fix that.

**User:**
would that nvim fix work for rex as much as cmux?

**Assistant:**
Yes. The fix doesn't involve the multiplexer at all: the agent talks straight to nvim's socket, so it works the same under Rex, cmux, tmux or plain Ghostty.

A few things do differ by host:

- **Finding the socket.** Agents started inside nvim's `:terminal` already have `$NVIM` set, so they can reach their parent nvim with no setup. Anything outside nvim needs the socket path. You can pin it per repo with `nvim --listen /tmp/nvim-<repo>.sock`.
- **Persistence.** This is where Rex comes out ahead. Under Rex, nvim and its socket keep running when you close the app, so the setup survives. As far as I know, cmux doesn't keep processes running once the app quits, so nvim and the agents die with it. I haven't confirmed that.
- **Remote hosts.** The socket is local to the machine nvim runs on. If you run nvim on a remote Rex host such as a Sprite, the agents have to run there too. That happens automatically when they're nvim's own terminal splits.
- **Combining the two.** With Rex, you can use both layers. nvim's socket handles reading and typing into the agents inside nvim. `rex capture` and `rex send` handle anything in a separate Rex pane, like a dev server or a shell.

**`$NVIM` is not global.** Each Neovim instance runs its own socket server, and sets `$NVIM` to that socket's path only in the terminals it opens. So:

**1. The editor registry**
It was part of the "doorbell," a design from before the host decision, written up in `md/docs/role-of-neovim.md` §10:
- **What it was:** each running Neovim would write a small file to `~/.local/state/agent-files/editors/<pid>`, holding its socket path and working directory.
- **What it was for:** when a thread changed, a ringer program (`agent-files-ring`) would read those files, find the Neovims open on that thread, and tell them over their sockets to re-read it, or alert you.
- **Why it was dropped (2026-11-01):** its only job was attention, and other things covered it. TUIOS's Inbox handled harness sessions, and agents.nvim's file watcher already notices agent-files' own threads changing within milliseconds.
- **Why AGENTS.md forbids it:** that file lists dropped pieces by name so a later agent doesn't rebuild them. It's a guard against coming back to the same idea, not a judgment on it.

This plan shares the mechanism (finding Neovims by socket) but not the purpose (addressing terminals, not alerts). It also writes no files. That's why I recommend you treat it as a different thing. Q1 asks you to confirm.

**4. Why replace `nvim`**
- **For:** any Neovim started without the launcher is unreachable, and you'd only find out when an agent can't find it. Replacing `nvim` means you never have to remember a second command.
- **Against:** quick one-off edits also get sockets and show up in `peers`. `peers` shows each one's working directory, so they're easy to tell apart, and their sockets disappear when they exit.
- **A limit:** a shell function only covers `nvim` typed in your interactive shell. Programs that start Neovim themselves, like `git commit` through `$EDITOR`, bypass it. Those are exactly the short-lived edits you'd want left out anyway, so the function happens to cover the Neovims you'd want to address and skip the ones you wouldn't.
